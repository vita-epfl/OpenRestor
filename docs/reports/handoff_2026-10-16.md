# Handoff — 16 October 2026

OpenRestor is an open benchmark for musical audio restoration: four evaluation sets, three
public and one organizer-only, three paired against a clean reference and one not. This note
is what a successor needs that the code and the roadmap do not already say.

Read `OpenRestor.md` for the design and `OpenRestor_Split_Roadmap.md` for the phase-by-phase
plan. This file covers the current state, the traps, and what blocks what.

## Where the four sets stand

| Set | State | Size |
| --- | --- | --- |
| Diagnostic (paired, one of 21 classes per item) | rendered, validates end to end (`status: complete`) | 542,829 examples, 648 shards, 2.3 TB + 128 GB clean |
| Blind-Synthetic (paired, 0–3 classes per item) | rendered, 60/60 slices | 25,849 examples, 7.95% left clean, 128 GB |
| Blind-Real Public (unpaired, real degradation) | built, curated by listening, packaged | 113 items, 210 clips, 70 min, 678 MB |
| Official Hidden paired evaluation | Montreux Jazz Festival candidate; written rights approval required before ingestion | — |

Blind-Real also has a **clean control set**, 92 items and 172 clips, excluded from scoring.
It exists because a set made only of degraded audio cannot show whether a system damages
audio that was already fine.

**Nothing has been run against any of this.** Phase 4, baselines, is not started, and it is
now the bottleneck: the benchmark has no evidence that it discriminates between systems.

## Three things that must not be renamed or edited

The project was renamed from OpenRestore to OpenRestor on 15 October 2026. Two identifiers
deliberately keep the former spelling, and a third item is a pending decision. Each is
commented where it lives, and `docs/benchmark_contract.md` records them.

1. **`configs/releases/private_v0_1.yaml`.** Its SHA-256 is recorded as
   `release_config_sha256` inside the frozen plan. Editing the file at all, even a comment,
   makes the release fail its own validation. A first rename pass changed it anyway despite
   an exclusion filter; comparing the three frozen hashes against the plan is what caught
   it. Do that check after touching anything under `configs/`.
2. **The `openrestore.*.v0.1` format strings** in `openrestor/degradations/release.py` and
   `pipeline.py`. They are written as an HDF5 attribute into each of the 648 shards and into
   every receipt, and the shard check compares them literally. Renaming them makes 2.3 TB
   unverifiable. A future format revision corrects the spelling along with its version.
3. **The repository directory is still `OpenRestore`.** Renaming it would break the absolute
   paths recorded throughout the frozen receipts and in `private_output_root`. Left as a
   separate decision.

## Licences: what was verified, and what it forbids

Publishing a rendered corpus redistributes its source audio in modified form, so each
source's licence governs its own examples. **Both sides of a pair are derivatives**: the
clean side is a 30-second excerpt with `loudnorm I=-18 LRA=11 TP=-1.0` applied — milder than
the degraded side, but a derivative, so a NoDerivatives term bars both.

| source | examples (Diagnostic / Blind-Synthetic) | terms, verified 15 Oct 2026 | published |
| --- | --- | --- | --- |
| SonicMaster clean | 525,000 / 25,000 | collection labelled CC BY 2.0; current Jamendo audit found only 856 CC BY IDs | **no, pending clarification** |
| Song Describer | 14,805 / 705 | per track: 209 of 705 NoDerivatives, 301 NonCommercial, 195 unrestricted | no |
| MUSDB18-HQ | 3,024 / 144 | academic use only; mixed CC BY-NC-SA; 100 tracks of unclear provenance | no |

Song Describer is the cautionary case. Its Zenodo page says CC BY-SA 4.0 and its paper calls
the recordings "permissively licensed", but `audio_licenses.txt` describes each track
separately and 72% carry NonCommercial or NoDerivatives. **A dataset-level licence label
cannot be trusted to describe the audio.** Per-track results are in
`build/sdd_track_licences.json`.

Nothing edits the frozen releases to act on this. `configs/releases/publication_policy_v0_1.yaml`
holds the decision and the evidence per source, and `scripts/build_publication_subset.py`
derives a publication index per corpus. Partitions are single-source, so withholding a
source withholds whole directories and no shard is rewritten. The completed Jamendo audit
found only 856 current CC BY IDs and left 8,856 unresolved, so all synthetic audio stays
withheld until written confirmation covers the underlying recordings or a much smaller
per-track subset is approved and repackaged.

Blind-Real Public is packaged with 208 CC BY clips, 2 CC0 and complete attribution for
the scored test, but its Internet Archive licence tags are uploader assertions, not
independent proof of rights; provenance sign-off remains necessary before upload.

Hosting is **EPFL DASH** (`datasets.epfl.ch`): the unit creates an S3 bucket through
`portal-xaas.epfl.ch`, then RCP configures a read-only link. The service is free, the S3
storage is billed under the u1 model, and the volume is unresolved — roughly 2.4 TB if both
synthetic corpora ship as audio. **The audio ships, not a generation recipe**: the
degradation tools exist so users can degrade their own audio, not so they must build the
distributed datasets.

## Metrics

Implemented, in the GPU perceptual pack: CLAP embeddings, FADTK (`clap-laion-music`, local
clean and built-in FMA-Pop references), and Audiobox Aesthetics (CE/CU/PC/PQ).

**Proposed for Blind-Real, pending ratification** (roadmap, Phase 2C): the reported figures
are `fadtk_fma_pop_distance` and Audiobox Aesthetics, each computed on input and output so
the number is a change rather than an absolute, plus a second FAD against the clean control
set as reference — 92 items of the same provenance and genre mix, far better matched than
FMA-Pop, whose distance partly measures distance from pop rather than from clean. The same
two metrics on the clean control set are the over-processing check.

**Disproved, and demoted on evidence:** the six no-reference signal descriptors in
`openrestor/metrics/blind_real.py` separate a listener's own degraded and too-clean verdicts
at chance — AUC 0.35 to 0.56 over 120 against 49 clips, with the noise floor pointing the
wrong way, because "clean" to an ear means well captured and well mixed rather than quiet.
A descriptor that cannot detect degradation cannot score its removal. They stay as
diagnostics only. Measurements in `build/blind_real/descriptor_separation.json`.

**Do the resolution experiment before adopting any distributional metric.** Split a clean
reference set into disjoint halves of 210 clips and compute FAD and KAD between them
repeatedly; that is the noise floor. If it exceeds the gap between the systems to be ranked,
no choice of reference saves the metric. One GPU hour, and it decides whether the whole
distributional approach is viable at this set size. KAD (MMD-based, ICML 2025) claims better
small-sample behaviour than FAD and is the likely primary; VISQOL is full-reference and
cannot be used on Blind-Real at all.

## How this project goes wrong

Every serious error here had the same shape: **a failure that reported itself as a clean
result.** Not a crash, not an exception — a plausible number.

- An AcoustID screen printed "0 of 195 identifiers match a commercial release" while all 195
  lookups had failed, because `fpcalc` was not installed. An unscreened set read as screened.
- 45 items entered the Blind-Real scored set because nothing had rejected them. Being left
  over is not a verdict.
- The per-artist cap silently promoted unheard items of the same act to replace rejected
  ones, including the same concert under a second identifier.
- A licence survey reported 56 rooms as having no licence field when the requests had simply
  failed.

The habit that caught all of them is to **ask what the result would look like if the step had
not run at all**, and to make that case loud. `scripts/validate_blind_real_release.py`
(1,922 checks) and `tests/test_publication_policy.py` exist for exactly this: the policy test
fails if a source in the release has no decision, because a source with no entry would
otherwise be published by default.

Two related habits, both now enforced: a copyright screen checks for its fingerprinter
before starting and refuses to summarise if lookups failed; and the publication build
reconciles every scored item against the recorded verdict files and exits rather than
shipping audio nobody decided on.
